# NOVA API Contract

## Base API

The backend exposes a synchronous HTTP API.

Primary endpoint:

POST /api/v1/ask

Health endpoint:

GET /health

The frontend sends a question and waits for the final answer in the same HTTP request.

No polling or background job mechanism is currently used.

---

## POST /api/v1/ask

### Request

Content-Type:

application/json

Request body:

{
  "question": "string"
}

Example:

{
  "question": "Türkiye'de son dönemde konut kredisi faiz oranları nasıl değişti?"
}

### Request Fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| question | string | yes | Natural-language user question sent to the NOVA agent |

---

## Successful Response

HTTP status:

200

Response body:

{
  "success": true,
  "data": {
    "answer": "string"
  },
  "error": null
}

Example:

{
  "success": true,
  "data": {
    "answer": "Konut kredisi faiz oranları ilgili dönemde ..."
  },
  "error": null
}

### Successful Response Fields

| Field | Type | Description |
| --- | --- | --- |
| success | boolean | true when the agent completed successfully |
| data | object | response payload |
| data.answer | string | final user-facing answer generated by the agent |
| error | null | null for successful requests |

---

## Agent / Runtime Error Response

Agent execution errors currently use HTTP status 200 with an application-level error envelope.

Response body:

{
  "success": false,
  "data": null,
  "error": "error message"
}

Example:

{
  "success": false,
  "data": null,
  "error": "External data source request failed."
}

The frontend must therefore inspect the `success` field and must not rely only on the HTTP status code.

---

## Hard Timeout Response

The application has a server-side hard wall-clock timeout.

Default:

REQUEST_HARD_TIMEOUT_SECONDS=100

When the request exceeds this limit, the API returns:

{
  "success": false,
  "data": null,
  "error": "İstek zaman aşımına uğradı, lütfen tekrar deneyin veya soruyu sadeleştirin."
}

The frontend should display this as a recoverable request error and may offer the user a retry option.

The timeout is intentionally lower than the deployment platform timeout.

---

## Validation Errors

FastAPI performs request schema validation before the request reaches the agent.

For example, if `question` is missing:

{}

FastAPI returns HTTP 422 with its standard validation response format.

This differs from the NOVA application-level response envelope.

Example shape:

{
  "detail": [
    {
      "type": "...",
      "loc": [
        "body",
        "question"
      ],
      "msg": "...",
      "input": "..."
    }
  ]
}

Frontend handling must therefore support both:

1. HTTP 200 with `success=false`
2. HTTP 422 FastAPI validation errors

## GET /health

### Request

GET /health

No request body is required.

### Response

HTTP status:

200

Example:

{
  "status": "ok",
  "message": "NOVA Backend çalışıyor."
}

This endpoint may be used for deployment health checks.

## Response Timing

The API is synchronous.

Observed slow EVDS-backed requests have reached approximately:

57.65 seconds

The backend hard limit is:

100 seconds

The deployment platform must allow more than 100 seconds so that the application can return its own controlled timeout response.

Current timeout hierarchy:

| Layer | Timeout |
| --- | ---: |
| Railway no-data HTTP limit | 300 s |
| NOVA API hard timeout | 100 s |
| EVDS HTTP request | 75 s |
| MIA / OpenAI-compatible HTTP request | 60 s |
| web_url_reader HTTP / Playwright | 15 s |
| DDGS web_search | 5 s |

Local Faz B verification results:

- EVDS slow-success request: 18.72 seconds
- Controlled hard-timeout verification with temporary 5-second configuration: 5.02 seconds
- Previously observed slow EVDS request: approximately 57.65 seconds
- Production application hard limit: 100 seconds

These measurements are individual verification samples, not a statistically meaningful average benchmark.

Frontend code should therefore not assume that all responses complete within a few seconds.

## CORS

Wildcard CORS is not used.

Allowed development origin:

http://localhost:3000

The deployed frontend origin is configured through:

FRONTEND_ORIGIN=https://<frontend-domain>

The backend allows:

GET
POST

Request headers are allowed as required by the frontend.

---

## Credentials

CORS credentials are disabled:

allow_credentials=False

The current API does not require browser cookies or session credentials.

The frontend should not use:

credentials: "include"

unless the authentication architecture changes later.

---

## Frontend Integration Example

Request:

fetch(`${API_BASE_URL}/api/v1/ask`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    question: userQuestion
  })
})

Expected success handling:

const payload = await response.json()

if (!response.ok) {
  // Handle HTTP-level errors such as FastAPI 422 validation errors.
}

if (payload.success === false) {
  // Handle NOVA application-level error or timeout.
}

const answer = payload.data?.answer

---

## Important Frontend Rules

1. Treat `/api/v1/ask` as a synchronous request.
2. Do not assume a short client timeout such as 10 or 30 seconds.
3. The frontend/proxy timeout should be greater than the backend 100-second hard timeout.
4. Inspect the `success` field even when HTTP status is 200.
5. Handle FastAPI HTTP 422 validation errors separately.
6. Do not send browser credentials unless the backend authentication model changes.
7. Configure the real deployed frontend domain through `FRONTEND_ORIGIN`.
8. Do not use `*` as the production CORS origin.
